### 精确崩溃时点

| 时点 | 自动恢复状态 | 为什么 |
| --- | --- | --- |
| 预占已提交，尚未派发 | `released` | 实验确认尚未调用上游，可释放预占 |
| 派发记录已提交，网络调用尚未发出 | `pending_usage` | 持久状态无法区分随后是否发出；恢复采用保守策略 |
| 首个流式事件已发出 | `pending_usage` | 上游已经执行，完整用量未知 |
| 已解析 usage，尚未提交结算 | `pending_usage` | 内存里的回执随进程丢失，需要核对，而不是推测为 0 |
| 结算已提交，回答尚未返回 | `settled` | 请求、用量和回放内容已持久化，重试直接回放 |
| 数据库停止，回执落盘后终止 | 回放后 `settled` | 本地持久回执保留已知用量；重复回放由事务与唯一约束处理 |

实验中的待核对请求根据受控上游证据明确补录或退款，再执行最终对账。自动恢复阶段和人工核对阶段分别验证。

## 新发现并修复的两个问题

### 缓存回放的慢客户端阻塞

新生成 SSE 已有逐写超时，但旧实现对普通响应和缓存回放直接整块 `Write`。用约 3.58 MB 的缓存响应、实际 8192 字节的 TCP 接收缓冲区测试，客户端不继续读取时，6 秒观察窗口内并发槽位仍被占用。

修复统一使用 Go `http.ResponseController.SetWriteDeadline` 与受限 `Flush`。同样的测试在实例的 2 秒写超时附近释放槽位，整个回归约 2.73 秒完成。两次测试均未额外调用上游，账户都只结算原来的 12 Token。

证据：`checks/slow-reader-before.json`、`checks/slow-reader-after.json`。源代码：[响应与流式写入](../internal/gateway/proxy.go)。

### 提交确认后客户端断连，丢失预占身份

原实现确认预占提交后，再用客户端上下文查询请求记录。精确回归在 `reserve_commit` 确认时取消上下文，复现得到 `fresh=true`、空请求 ID 和 `context canceled`。调用方因此无法接续释放已提交预占。

修复直接返回已确认提交的请求身份，消除提交后的可取消查询。Go/MySQL 回归由失败变为通过，HTTP 实验也验证在实例存活时断连可以释放预占，且上游调用数为 0。

证据：`logs/reserve-cancel-before.log`、`checks/go-test.jsonl`。源代码：[Reserve](../internal/gateway/store.go)。这里验证的是提交结果已经确认后的取消；提交确认本身丢失的网络故障仍要结合事务回执与对账处理。

### 如何判断瓶颈

新增 `llmgw_stage_seconds` 记录鉴权、限流、渠道查询、预占、派发、上游、结算、响应写入，以及各事务提交和账户锁等待。阶段数据中，数据库提交耗时明显高于鉴权、Redis 和受控上游响应；保留同步持久化设置，没有降低刷盘级别换取结果。

`reserve` 包含 `reserve_commit`，不能把父子阶段均值直接相加。流式的 `upstream` 覆盖桥接过程，应结合 `stream_write` 与首事件耗时阅读。CPU 采样组单独列出，其他四组未执行 CPU 采样。

原始目录：`/data/zjr/llm_gateway/checks/perf/20261111T074441Z/`。每组包含 `k6-summary.json`、`measurements.json`、`k6.log`；采样组另有 `cpu.pprof`、`cpu-top.txt`、`heap.pprof`、`goroutine.pprof`。数据用于分析网关与存储，模型推理性能需要另外测量。

## 提交延迟的进一步定位（2026-11-12 / 13）

沿用同步提交 `innodb_flush_log_at_trx_commit=1`、`O_DIRECT` 和原有到达率、VU、SLO。采集器按同一时间轴保留以下数据：

- 网关 `/metrics` 每 5 秒采一次阶段统计与连接池状态。连接池指标直接复用 Prometheus 的 `NewDBStatsCollector`，包含占用数、等待次数与累计等待时长。
- 每秒采集 `/data` 所在分区及其物理磁盘的吞吐、在途请求、完成请求平均等待、宿主机 PSI、目标进程 I/O 和 CPU 计数、cgroup 内存事件。压力升高时记录本项目数据库处于 D 状态的线程与内核等待位置。
- 每 5 秒异步读取数据库全局计数；独立设置 2 秒查询超时，数据库采集超时会留下记录，宿主机采样继续进行。
- 提交超过 250 ms 时保存事务阶段、请求 ID、开始时间与耗时。每个阶段每秒至多一条慢日志，直方图仍计入每次操作；日志不记录 API Key、幂等头或提示词。
- `gateway-samples.jsonl` 和 `host-samples.jsonl` 增量追加；完整 `measurements.json` 在一组结束时落盘，避免每 5 秒重写不断增长的采样历史。

每组结束后自动生成 `latency-diagnostics.json`，对提交均值最高的五个窗口关联磁盘等待、I/O 压力、连接池等待与进程写入量。阶段窗口均值与磁盘采样峰值采用不同口径；共享磁盘数据用于判断相关性，定位具体外部写入进程还需要对应进程的观测。

本机用户服务层实际下放的控制器是 `memory pids`。该层没有 `cpu.max` 与 CPU 节流计数，报告会将节流数据标为缺失。`CPUQuota` 保留为服务配置值；本轮生效的资源约束包括内存上限及 Go 自身的 `GOMAXPROCS` 并行度设置。

## 源码阅读与技术追问

1. [proxy.go](../internal/gateway/proxy.go)：从 `chat` 到 `forward`，说明准入、预占、派发和结算的顺序。模型网络调用位于数据库事务之外。
2. [store.go](../internal/gateway/store.go)：对照 `Reserve`、`Dispatch`、`Finish`。账户锁负责并发预占，唯一约束限制重复账本事件，事务原子更新请求、计数与账本。
3. [models.go](../internal/gateway/models.go)：区分预占估算、实际用量、请求结果和未知状态。当前允许实际消耗形成负额度，随后阻止新调用；严格硬额度还需要准确 Token 预算及相应策略。
4. [diagnostics.go](../internal/gateway/diagnostics.go)：解释管理鉴权、采样时长限制及精确检查点。检查点让崩溃位置可重复，避免用 sleep 猜测。
5. [server.go](../internal/gateway/server.go)：查看持久回执、原子落盘、回放与租约恢复；结合旧版心跳死锁理解为什么采用独立实例租约表。

可用以下问题复练：

- 为什么幂等键按账户隔离？同键不同内容为什么返回冲突？
- Redis RPM 和数据库额度账本各自保证什么？
- 为什么不能在长时间模型调用期间持有数据库事务和账户锁？
- 网关失联后，如何区分可释放、已结算和需要核对的请求？
- 模型已经执行，但客户端没有收到回答时，重试如何避免再次调用和扣额？
- 写超时、空闲超时、总超时和取消传播分别解决什么问题？
- 为什么租约心跳与结算更新请求状态可能形成索引锁冲突？
- 怎样区分发压不足、热点账户锁等待、事务提交慢和模型慢？
