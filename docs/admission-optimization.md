# 请求提交次数优化与性能对照

## 问题与改动

2026-11-13 的 30 分钟长测计划 18000 次，成功发出 17970 次，另有 30 次迭代未发出。I/O 压力、磁盘等待、数据库提交耗时和连接池等待位于相同时间窗口。正常成功请求原先需要三个事务提交：

```text
split：额度预占 COMMIT → 首次派发 COMMIT → 调用模型 → 用量结算 COMMIT
combined：额度预占 + 首次派发 COMMIT → 调用模型 → 用量结算 COMMIT
```

优化将首个派发意图、价格快照和 attempt 记录加入预占事务。初版复用 `dispatchTx`；长测发现恢复索引锁冲突后，候选修复改为首次写入最终状态、按主键补齐派发信息，备用渠道仍使用 `dispatchTx`。正常单次成功调用由 3 次事务提交降为 2 次；渠道失败后再派发仍单独提交。数据库继续使用 `innodb_flush_log_at_trx_commit=1` 与 `O_DIRECT`。

提交次数与底层 fsync 次数分别记录：数据库可以合并多个事务的刷盘，单请求提交次数减少 1/3 不等于物理 fsync 或时延必然减少 1/3。事务实现使用 Go 标准库 `sql.Tx`，依据 [Go 事务说明](https://go.dev/doc/database/execute-transactions) 将相关 SQL 操作放在同一事务内；持久化设置见 [MariaDB InnoDB 文档](https://mariadb.com/docs/server/server-usage/storage-engines/innodb/innodb-system-variables#innodb_flush_log_at_trx_commit)。

## 正确性与代价

- 幂等检查和额度检查仍持有账户、Key 及请求行锁。只有新的、额度充足的请求才选择首个渠道；重复请求直接读取持久记录，不消耗熔断半开探针。
- 渠道选择仅做内存路由、熔断许可和 SDK 客户端构造，事务内没有模型网络调用。提交确认后才调用模型。
- 派发 SQL 失败时，预占计数、请求、账本和 attempt 一起回滚；提交确认后直接返回请求及 attempt 身份，避免再用可能取消的上下文查询。
- 活进程确认尚未发出模型请求时取消，可使用零用量回执释放预占。进程在合并提交后崩溃时，持久状态已经包含派发意图，恢复为 `pending_usage` 并保留额度等待核对；该边界不再存在 split 模式单独的“已预占、未派发”持久状态。
- 新增 `after_admit` 故障检查点，验证模型调用数在该点为 0；崩溃后仍保守保留未知用量。旧 `after_reserve` 检查点留给 split 模式。
- 账户与账本结算、SSE、持久回执与唯一约束继续复用原流程。正常成功调用的两次提交均确认后，业务链路才完成对应持久化步骤。

配置 `LLMGW_ADMISSION_MODE=split|combined`，默认 combined。`/metrics` 的 `llmgw_admission_info{mode="..."}` 显示进程实际模式。阶段直方图新增 `admit_commit`，原有 split 阶段计时继续保留。

## 2026-11-14：查询连接隔离与限流重试

针对上轮 25 次鉴权、2 次渠道查询超时和 6 次限流存储失败，本轮修改请求入口的资源分配和重试语义。

### 固定连接总额，分配查询专用池

`LLMGW_METADATA_DB_CONNECTIONS=2` 从数据库连接总额度中划出两个连接，用于鉴权和渠道查询。负载实例总额度 16 时，事务池为 14、查询池为 2；两个池使用相同 DSN 和数据库。事务仍在持有行锁时重新检查 Key 状态，吊销行为继续由数据库保证。配置为 0 可恢复共享池对照。

查询的连接等待和 SQL 执行分别记录为 `metadata_acquire`、`authenticate_query`、`providers_query`；两个池分别使用 `db_name=gateway` 和 `db_name=gateway_metadata` 的 `go_sql_*` 指标。查询继续遵守原有 1 秒预算。事务池占满时，查询拥有独立的连接额度；数据库整体阻塞时，两组连接仍会受到同一存储的影响。

### 单次限流操作具有可重试身份

每次 HTTP 限流检查生成服务器内部随机操作 ID，在原有 Redis Key 中同时写入窗口、计数和该操作的结果。计数与结果用一次多字段 `HSET` 更新，避免脚本后续命令出错后，计数已变更而操作结果缺失。设计依据是 Redis 脚本的隔离执行语义，以及执行错误后已完成命令不会自动回滚的行为，参见 [Redis 脚本说明](https://redis.io/docs/latest/interact/programmability/eval-intro/)、[HSET](https://redis.io/docs/latest/commands/HSET/) 和 [Redis 事务回滚说明](https://redis.io/blog/you-dont-need-transaction-rollbacks-in-redis/)。

操作结果逻辑保留 120 秒，优先于分钟窗口切换检查；即使重试跨过分钟边界，也复用首次结果。过期字段通过增量 `HSCAN` 清理，主 Hash 设 180 秒 TTL。客户端 `Idempotency-Key` 仍表示模型请求身份，每次新的 HTTP 请求继续消耗一次 RPM；网络层重试使用同一个内部操作 ID。

`LLMGW_RATE_LIMIT_TIMEOUT_MS=3000` 限制整个限流过程。第一次尝试最多使用一半预算；可恢复的网络错误触发一次 25–50 ms 退避，第二次使用剩余预算，驱动隐式重试关闭。持续断连在总预算内失败，脚本数据错误直接失败。新增尝试、重试和结果复用计数，以核验实际执行路径。
